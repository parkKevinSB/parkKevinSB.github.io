항만 터미널에서 TOS가 작업 계획과 지시를 관리한다고 해서 크레인이 바로 움직이는 것은 아니다. 업무 지시를 실제 장비가 이해하는 명령으로 바꾸고, 장비의 수락·진행·완료 상태를 추적해 다시 TOS에 반영하는 실행 계층이 필요하다. 내가 유지보수해 온 ATCSS가 그 역할을 담당한다.

<!--more-->

## ATCSS는 TOS와 ECS 사이의 실행 오케스트레이터다

TOS는 어떤 컨테이너를 어디에서 어디로 옮길지 지시한다. ECS는 야드 크레인을 실제로 제어한다. 두 시스템 사이에서 ATCSS는 다음 흐름을 책임진다.

1. TOS의 작업 생성·갱신·취소 지시를 수신한다.
2. 컨테이너와 야드 위치, 장비 상태, 운영 조건을 검증한다.
3. 실행 가능한 작업을 선별하고 장비에 배차한다.
4. ECS가 수행할 작업 명령을 만들고 전송한다.
5. 명령 수락, 실행, 완료 또는 중단 상태를 추적한다.
6. 데이터베이스의 작업·장비·재고 상태를 갱신하고 결과를 TOS에 보고한다.

그래서 ATCSS는 메시지를 그대로 전달하는 중계기가 아니다. TOS가 보는 업무 상태와 ECS가 보고하는 물리 장비 상태 사이의 차이를 조정하고, 작업이 끝까지 이어지도록 책임지는 상태 기반 실행 시스템에 가깝다.

## 레거시 시스템에서 중요한 것은 상태의 경계였다

분석한 시스템은 Java와 Spring Framework, eGovFrame, MyBatis를 사용하고 Oracle·MSSQL 데이터베이스, Quartz 스케줄링, TCP 소켓 통신으로 구성되어 있다. 오랫동안 여러 현장에 적용되면서 공통 업무 로직과 사이트별 장비 프로토콜·운영 규칙이 함께 축적된 구조다.

운영 중에는 정상 흐름보다 경계 상황이 더 어렵다.

- 같은 작업 지시가 다시 들어왔을 때 중복 실행을 막아야 한다.
- 실행 중 작업의 갱신이나 취소가 들어오면 ECS 상태와 맞춰야 한다.
- ECS 연결이 끊겼다가 복구되면 남아 있는 명령을 확인해야 한다.
- 장비에서는 완료됐지만 TOS 보고가 실패하면 안전하게 재시도해야 한다.
- 컨테이너 위치와 작업 상태가 서로 다른 시점에 갱신되어도 야드 재고가 어긋나지 않아야 한다.

유지보수에서는 개별 오류를 막는 것뿐 아니라, 어느 시스템이 현재 상태의 기준인지와 실패 후 어디서 다시 시작할지를 명확히 하는 것이 중요했다.

## 네 개 터미널을 유지보수하며 사이트 차이를 다뤘다

국내 2개, 일본 1개, 중동 1개 터미널의 ATCSS 운영 유지보수를 담당했다. 같은 제품을 사용하더라도 현장마다 TOS 메시지, ECS 장비 프로토콜, 데이터베이스 구성, 야드 배치와 운영 규칙이 다르다.

코드에는 공통 작업·장비·재고 관리 계층과 사이트별 Spring 컨텍스트, 메시지 처리기, 장비 명령 구현이 분리되어 있다. 유지보수할 때는 공통 로직의 수정이 다른 현장에 미칠 영향을 확인하면서도, 특정 터미널의 요구는 가능한 한 사이트 경계 안에서 처리해야 했다.

이 과정에서 작업 생성·배차·완료 보고, 장비 상태 동기화, 자동 재취급과 이동 작업, 차량 진입 조건 등 운영 중 발견된 문제를 분석하고 개선했다.

## 일본 신규 터미널은 개발부터 롤아웃까지 맡았다

기존 ATCSS 제품 전체를 내가 처음부터 개발한 것은 아니다. 다만 일본 신규 터미널 한 곳은 기존 제품을 출발점으로 현장별 기능을 개발하고 실제 운영에 적용하는 과정까지 직접 수행했다.

현장의 TOS와 ECS 인터페이스, 데이터베이스와 설정, 작업 실행 규칙을 분석해 사이트 구현에 반영했다. 이후 연동 시험에서 발견된 상태 차이와 예외 흐름을 수정하고, 배포와 롤아웃까지 이어 갔다. 기존 시스템을 읽는 능력뿐 아니라 현장 요구를 제품 구조 안에 안전하게 넣고 운영 전환까지 책임지는 경험이었다.

## ECS 에뮬레이터로 실제 장비 투입 전에 검증했다

신규 사이트를 검증할 때 실제 크레인을 항상 사용할 수 있는 것은 아니다. 장비 사용 시간이 제한되고, 오류나 통신 단절 같은 상황을 실제 설비에서 반복하기도 어렵다.

그래서 ECS의 통신과 작업 상태를 재현하는 에뮬레이터를 직접 만들었다. TOS 작업 지시가 ATCSS를 거쳐 ECS 명령으로 바뀌는 과정, 명령의 수락과 진행·완료 보고, 오류와 재접속 상황을 반복 실행할 수 있게 했다.

에뮬레이터는 단순히 정상 응답을 반환하는 가짜 서버가 아니었다. 작업 상태와 장비 상태를 가진 검증 대상의 반대편 시스템으로 동작해야 했다. 이를 통해 실제 크레인 투입 전에 인터페이스와 상태 전이 문제를 발견하고 수정할 수 있었다.

## 오래된 기술보다 운영 책임의 범위가 중요했다

기술 스택만 보면 최신 시스템은 아니다. 하지만 24시간 운영되는 항만 시스템에서는 프레임워크의 연식보다 기존 동작을 깨뜨리지 않고 문제를 재현하며, 여러 시스템의 상태를 끝까지 일치시키는 능력이 중요하다.

이 경험을 통해 다음 기준을 갖게 됐다.

- 공통 로직과 사이트별 변경의 경계를 먼저 찾는다.
- 메시지 한 건보다 작업 생명주기 전체를 본다.
- 정상 처리와 함께 취소·재시도·재접속·복구 경로를 설계한다.
- 실제 장비가 없어도 검증 가능한 반대편 시스템을 만든다.
- 개발 완료가 아니라 현장 롤아웃과 안정화까지를 한 작업으로 본다.

ATCSS 유지보수와 신규 사이트 개발은 장비 제어 경험을 분산된 업무 시스템의 상태 관리로 확장한 프로젝트였다. 이후 에뮬레이터와 자동화 백엔드를 설계할 때도 이 실행 흐름과 복구 관점이 기준이 되고 있다.

> 고객과 운영 보안을 위해 터미널명, 내부 사이트 코드, 메시지 전문, 네트워크와 운영 수치는 공개하지 않는다.
