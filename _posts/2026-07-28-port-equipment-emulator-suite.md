항만 자동화 소프트웨어는 장비가 연결되어야 비로소 확인할 수 있는 문제가 많다. 하지만 개발 기간 내내 실제 크레인을 사용할 수는 없다. 장비가 아직 준비되지 않았거나 현장 운영 중일 수 있고, 잘못된 명령 하나가 안전과 일정에 직접 영향을 줄 수도 있다.

2024년부터 이 간극을 줄이기 위해 ECS·STS 장비 에뮬레이터와 연동 검증 도구군을 직접 설계하고 구현했다. 목표는 화면에 움직이는 장비 모양을 보여주는 것이 아니었다. 상위 시스템이 실제 장비와 통신할 때 만나는 **명령, 상태 변화, 물리 제약, 오류와 재접속의 흐름**을 반복해서 검증할 수 있는 환경을 만드는 일이었다.

<!--more-->

## 무엇을 재현해야 하는가

에뮬레이터의 품질은 화면이 실제 장비와 얼마나 닮았는지가 아니라, 검증하려는 계약을 얼마나 충실히 재현하는지에 달려 있다. 그래서 먼저 다음 범위를 분리했다.

- 상위 시스템이 보내는 작업 명령과 제어 명령
- 장비가 보고하는 위치, 모드, 작업 단계와 오류 상태
- 주행·횡행·권상 축과 스프레더 같은 장치의 동작
- 컨테이너 픽업과 적치 전후의 물리 상태
- 복수 장비의 통신 세션과 현장별 프로토콜 차이
- 통신 단절, 재접속, 작업 거절과 중단 흐름
- RFID, 차단기, 센서 보정 등 주변 설비와의 연동

이 범위를 통신, 도메인, 작업 시퀀스, 화면, 데이터 서비스로 나눴다. 한 계층의 변경이 다른 계층으로 바로 번지지 않게 하고, 새로운 장비나 프로토콜을 추가할 때 기존 작업 흐름을 최대한 재사용하기 위한 구조다.

## ECS: 야드 크레인의 작업을 상태로 표현하다

ECS 에뮬레이터에서는 야드 크레인의 이동과 컨테이너 작업을 다뤘다. 단순히 현재 좌표를 목적지로 바꾸는 방식으로는 실제 작업을 검증하기 어렵다. 작업은 사전 조건 확인, 안전 높이 확보, 스프레더 크기 조정, 수평 이동, 픽업, 적치, 완료 보고처럼 여러 단계로 이어진다.

각 단계는 명시적인 상태를 갖는 시퀀스로 구성했다. 장비가 자동 운전 상태인지, 이미 다른 작업을 수행하고 있는지, 스프레더에 컨테이너가 있는지, 이동 경로에서 다른 장비와 간섭하지 않는지를 먼저 확인한다. 간섭 조건이 해소되지 않으면 바로 다음 단계로 넘어가지 않고 대기하거나 다시 검사한다.

터미널의 블록·베이·행·단 위치는 장비가 이동할 수 있는 좌표로 변환했다. 이 구조 덕분에 작업 명령의 논리적 위치와 화면에 표현되는 물리적 위치를 같은 모델에서 다룰 수 있었다. 복수 장비와 현장별 차이는 공통 동작 위에 프로필을 추가하는 방식으로 분리했다.

## STS: 장비 동작과 작업 스케줄링을 함께 다루다

STS 에뮬레이터는 선박과 육상 사이에서 컨테이너를 옮기는 안벽 크레인의 흐름을 모델링한다. 갠트리, 트롤리, 호이스트, 스프레더의 움직임뿐 아니라 선박·플랫폼·차량 사이의 작업 연결이 필요하다. 단일 트롤리와 이중 트롤리 구성도 서로 다른 실행 흐름을 갖는다.

여기서는 장비 동작과 작업 선택을 분리했다. 스케줄러는 대기 중인 작업에서 실행 후보를 만들고 다음 조건을 검사한다.

1. 현재 크레인과 트롤리가 새 작업을 받을 수 있는가
2. 스프레더와 대상 위치의 물리 상태가 작업과 일치하는가
3. 선박 적재 순서나 상부 컨테이너 같은 제약을 만족하는가
4. 플랫폼 공간과 차량 도착 조건이 준비되었는가
5. 작업 순서와 이동 거리를 고려했을 때 어떤 후보가 우선인가

선택된 작업은 이동, 안전 확인, 픽업·적치, 센서 기반 미세 조정, 완료 또는 복구 단계로 이어진다. 스케줄러가 “무엇을 할지” 결정하고 시퀀스가 “어떻게 수행할지” 책임지게 하면서 두 영역을 독립적으로 시험할 수 있었다.

## 통신 코드는 연결보다 경계가 중요했다

장비 통신에는 비동기 TCP 소켓과 송수신 큐를 적용했다. 연결, 수신 누적, 메시지 분리, 파싱, 처리, 응답 생성을 각각 나누고, 복수 장비의 세션과 재접속 흐름을 관리했다.

프로토콜은 파서와 메시지 처리기, 업무 처리 로직을 분리했다. 같은 종류의 작업이라도 현장이나 장비에 따라 메시지 형식이 달라질 수 있기 때문이다. 형식의 차이가 작업 시퀀스 전체를 오염시키지 않도록 변환과 처리 경계를 따로 뒀다.

이 구조는 정상 응답만 확인하기 위한 것이 아니다. 연결이 끊긴 시점, 처리할 수 없는 명령, 늦게 도착한 상태, 중단된 작업처럼 운영에서 중요한 상황을 의도적으로 만들고 관찰할 수 있게 한다.

## 운영자가 사용할 수 있어야 했다

검증 환경은 개발자만 사용하는 통신 콘솔로 끝내지 않았다. WinForms 화면에서 장비의 위치와 상태를 확인하고, 줌과 이동으로 작업 영역을 탐색하며, 축과 스프레더를 수동으로 제어할 수 있게 했다. 작업 큐 활성화, 수동 완료, 운전 모드 변경 같은 운영 동작도 화면에서 시험할 수 있도록 구성했다.

또한 본체 에뮬레이터와 별도로 RFID, 차단기, 센서 보정, 외부 인터페이스를 검증하는 작은 도구들을 만들었다. 복잡한 통합 문제를 한 프로그램에서 모두 재현하기보다, 경계별로 입력과 응답을 독립적으로 확인하는 편이 원인을 찾기 쉽기 때문이다.

## 이 프로젝트에서 쌓은 것

이 작업을 통해 장비 한 대의 제어 로직을 넘어, 여러 장비와 업무 시스템이 함께 움직이는 검증 환경을 설계하는 경험을 쌓았다.

- 실제 장비 동작을 도메인 상태와 작업 시퀀스로 변환하는 방법
- 물리 제약과 운영 우선순위를 스케줄링 조건으로 표현하는 방법
- 복수 연결과 프로토콜 변형을 감당하는 통신 경계 설계
- 정상 경로뿐 아니라 중단·거절·재접속을 확인하는 테스트 관점
- 개발자와 운영자가 같은 상태를 확인할 수 있는 도구 구성

무엇보다 에뮬레이터는 실제 장비의 값싼 복제품이 아니라는 점을 배웠다. 좋은 에뮬레이터는 시스템 사이의 약속을 드러내고, 장비가 없어도 실패를 반복해 볼 수 있게 하며, 현장에서 처음 발견할 문제를 개발 단계로 앞당기는 소프트웨어다.

보안과 계약을 위해 이 글에서는 고객명, 내부 시스템명, 메시지 형식과 운영 수치를 제외했다.
