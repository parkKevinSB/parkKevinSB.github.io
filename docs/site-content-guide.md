# KevinPark 사이트 콘텐츠·운영 가이드

이 문서는 `parkKevinSB.github.io`를 수정하는 사람과 에이전트가 사이트의 방향을 일관되게 유지하기 위한 기준이다.

## 1. 사이트 목적

- 한국어 기술 블로그이자 경력 근거 저장소로 운영한다.
- 항만 자동화와 Java 백엔드를 중심으로 오픈소스, AI Agent, 장비 제어 개발 이력을 프로젝트 단위로 보관한다.
- 첫 화면에서는 현재 지향하는 항만 자동화·Java 백엔드·오픈소스 개발을 우선하고, 장비 제어 경험은 상세 경력과 프로젝트에서 사실 중심으로 설명한다.
- 향후 이력서와 포트폴리오를 작성할 때 확인할 수 있는 객관적인 경력 자료를 만든다.
- 표시 이름은 `KevinPark`를 사용하며 실명은 필요하지 않으면 적지 않는다.

## 2. 기본 표현 방식

- 한국인이 읽는 페이지이므로 본문은 한국어로 작성한다.
- 제품명, 라이브러리명과 기술 용어만 필요한 범위에서 영어를 사용한다.
- 홍보 문구, 감성적인 소개, 자기계발식 문장과 일기 형식은 사용하지 않는다.
- 확인한 사실을 짧고 명확하게 적는다. 추정한 내용을 경력 사실처럼 쓰지 않는다.
- 구현된 기능, 운영 중인 기능과 향후 확장 계획을 같은 상태처럼 섞지 않고 별도 항목으로 구분한다.
- `직접 개발`이라는 표현을 반복하지 않는다. 담당 범위와 산출물로 기여도를 보여준다.
- 파일 수, 클래스 수, 테스트 파일 수처럼 경력을 설명하는 데 도움이 적은 수치는 넣지 않는다.
- 불필요하게 내부 구현을 나열하지 않고, 시스템의 목적과 실제 처리 흐름이 이해될 정도로 설명한다.

## 3. 프로젝트 정리 기준

프로젝트 페이지는 다음 질문에 답할 수 있어야 한다.

1. 이 시스템 또는 프로그램은 무엇인가?
2. 어떤 업무나 장비를 처리하는가?
3. KevinPark가 맡은 범위는 무엇인가?
4. 주요 기능과 전체 처리 흐름은 무엇인가?
5. 어떤 기술을 사용했는가?
6. 실제 적용·롤아웃·현장 검증 범위는 어디까지인가?

다음 기여 유형은 서로 구분한다.

- 신규 개발
- 기존 시스템 유지보수
- 기존 시스템을 기반으로 한 신규 사이트 개발·롤아웃
- 개인 프로젝트
- 오픈소스 설계·개발
- 컨셉과 구조를 설계하고 에이전트를 활용해 구현한 프로젝트

기여 범위를 과장하거나 서로 다른 유형을 같은 표현으로 통일하지 않는다.

## 4. 페이지별 역할

### 메인 페이지

- 경력과 대표 프로젝트를 빠르게 파악하는 인덱스다.
- 객관적인 사실과 짧은 설명만 사용한다.
- 자세한 기능과 구조는 개별 프로젝트 페이지로 연결한다.

### 프로젝트 페이지

필요한 항목만 선택해 아래 순서로 구성한다.

1. 프로젝트 개요
2. 시스템 또는 장비의 역할
3. 담당 범위
4. 주요 기능
5. 처리 흐름 또는 구조
6. 기술 스택
7. 화면·장비 이미지
8. 적용 또는 검증 범위
9. 공개 범위

구조도는 관계나 실행 순서를 설명할 때만 사용한다. 단순한 내용을 장식 목적으로 도표화하지 않는다.

### 기술 기록

- 프로젝트에서 재사용할 수 있는 기술적 판단이나 구현 개념을 정리한다.
- 소설처럼 배경을 길게 쓰지 않는다.
- `대상 문제 → 적용 구조 → 핵심 동작 → 검증 결과` 순서를 기본으로 사용한다.
- 회사 내부 자료가 필요한 세부 구현은 생략하거나 일반화한다.

## 5. 공개 범위와 보안

이 저장소에는 웹사이트를 구성하는 Markdown, HTML, CSS와 공개용 이미지만 저장한다.

다음 내용은 올리지 않는다.

- 회사 또는 개인 프로젝트의 원본 소스 코드
- 로컬 소스 경로와 내부 저장소 주소
- 계정, 비밀번호, Token, 인증서와 접속 정보
- IP, 실제 Host, VPN·FTP 설정, Port와 원격 경로
- 실제 운영 로그 원문과 고객 데이터
- DB 접속 문자열, Schema, Table 구조, SQL 전문
- 비공개 고객명·사이트명·장비 식별자
- 회사 내부 모듈의 상세 구현과 미공개 프로토콜
- 허가 여부가 불명확한 문서·도면·이미지

로컬 프로젝트 코드는 경력 내용을 확인하기 위해 읽을 수 있지만, 분석 결과만 공개용 문장으로 다시 작성한다. 코드 일부를 복사하거나 원본 저장소를 이 사이트 저장소에 포함하지 않는다.

회사 프로젝트는 다음 수준으로 정리한다.

- 시스템의 공개 가능한 목적
- 담당한 모듈과 기능 범위
- 외부에서 이해할 수 있는 처리 흐름
- 사용 기술
- 적용·검증 여부

내부 클래스명, 세부 Action 목록, 정확한 업무 규칙과 고객별 설정은 공개하지 않는다.

## 6. 이미지 기준

- 사용자가 제공했거나 공개 사용이 확인된 이미지만 사용한다.
- 회사명, 개인정보, 실제 주소와 민감한 식별자는 가린다.
- 화면을 이해할 수 있는 정도로 해상도를 낮추되 본문 카드 크기는 기존 페이지와 맞춘다.
- 페이지에 `공개용으로 해상도를 축소했다`는 설명은 적지 않는다.
- 이미지 안의 긴 설명은 가능한 한 본문 텍스트로 옮긴다.
- AI가 만든 장식용 이미지와 의미 없는 일러스트는 사용하지 않는다.
- 이미지에는 화면의 역할을 설명하는 대체 텍스트를 작성한다.

## 7. 디자인 기준

- 밝은 배경과 흰색·옅은 회색을 기본으로 사용한다.
- 포인트 색상은 현재의 청색 계열을 제한적으로 사용한다.
- 카드와 도표는 테두리, 간격과 타이포그래피 중심으로 단순하게 만든다.
- 그림 안에 글을 억지로 넣지 않고 HTML 텍스트로 구성한다.
- 기존 레이아웃과 CSS 구성 요소를 우선 재사용한다.
- 데스크톱과 모바일에서 가로 넘침과 글자 겹침이 없어야 한다.

## 8. 검색 노출 정책

- 현재 사이트는 주소를 전달받은 사람이 확인하는 링크 공유용 포트폴리오로 운영한다.
- `_config.yml`의 `search_indexing` 기본값은 `false`로 유지한다.
- 검색 노출이 비활성화된 동안 공통 레이아웃에 `noindex, nofollow`를 출력한다.
- 사용자의 명시적인 요청 없이 검색 노출을 활성화하거나 해당 Meta Tag를 제거하지 않는다.
- `noindex`는 검색 결과 노출을 제한하는 설정이며, 주소를 통한 접속이나 외부 수집을 차단하는 보안 기능은 아니다.
- 검색 노출을 시작할 때는 공개 범위를 다시 검토한 뒤 `search_indexing`을 `true`로 변경하고 Sitemap과 검색엔진 등록 여부를 함께 검토한다.

## 9. 저장소 구조

- `index.html`: 메인 페이지
- `projects.html`: 프로젝트 목록
- `projects/*.md`: 프로젝트 상세
- `_posts/*.md`: 기술 기록
- `_drafts/post-template.md`: 기술 기록 초안
- `assets/images/projects/`: 공개용 프로젝트 이미지
- `assets/css/style.css`: 공통 디자인
- `_layouts/`: 공통 페이지 레이아웃
- `_config.yml`: Jekyll 및 사이트 설정

## 10. 수정 절차

1. 수정 요청과 관련된 기존 페이지를 먼저 읽는다.
2. 필요한 경우 사용자가 지정한 로컬 프로젝트를 읽기 전용으로 분석한다.
3. 확인한 사실과 공개 가능한 범위를 분리한다.
4. 관련 Markdown과 필요한 최소 CSS만 수정한다.
5. 내부 정보와 과장된 표현이 없는지 다시 확인한다.
6. Jekyll 빌드와 내부 링크를 확인한다.
7. 레이아웃을 변경했다면 데스크톱과 모바일 화면을 확인한다.
8. 관련 파일만 명시적으로 Stage하고 한국어로 간결하게 Commit한다.
9. `main`에 Push한 뒤 GitHub Pages 배포와 공개 페이지를 확인한다.
